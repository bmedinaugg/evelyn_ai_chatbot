# M3c Preprod Infrastructure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Everything needed to deploy preprod with one command once AWS access exists. That covers:
- a container image
- the API on Fargate behind CloudFront and WAF
- the widget on S3
- the nightly worker schedules
- SES
- a manual GitHub deploy workflow and a runbook

Nothing is deployed in this milestone (no AWS credentials on the dev machine).

**Architecture:**
- **One CloudFront distribution, one origin for the customer:**
  - `/` serves the widget: S3 bucket via Origin Access Control, built files uploaded by
    `BucketDeployment`.
  - `/widget/*` and `/health` go to the API: an **internal** ALB through a CloudFront **VPC origin**,
    so the ALB is never public and no custom domain or certificate is needed for preprod.
  - The widget and the API share an origin. The widget calls the API with relative URLs, and
    `WIDGET_ALLOWED_ORIGINS` is the distribution's own domain.
- **WAF** (CLOUDFRONT scope, so its own stack in us-east-1):
  - AWS managed rule sets: Common, Known bad inputs, IP reputation
  - a rate-based rule per IP on `/widget/*`
- **API service:**
  - Fargate, ARM64, 0.5 vCPU / 1 GB, desired 1, with deployment circuit breaker and rollback
  - **mock Magicline as a sidecar** container (preprod uses synthetic profiles only)
  - `TRUST_PROXY_HOPS=2` (CloudFront and ALB)
  - ingress only from the ALB security group
  - public IP for outbound calls (Claude, Supabase, Freshdesk, SES), no NAT
- **Secrets** (Secrets Manager, set by hand after the foundation deploy, never in code):
  - one JSON secret `app` with `ANTHROPIC_API_KEY`, `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`,
    `FRESHDESK_API_KEY` and `TURNSTILE_SECRET_KEY`
  - `OTP_HMAC_SECRET`, generated by CloudFormation
- **Worker:** the same image, run by EventBridge Scheduler (Europe/Amsterdam):
  - `sync-faq` at 02:00
  - `sync-ticket-topics` at 02:15
  - `retention` at 03:00
- **SES:** an email identity for `EMAIL_FROM` (preprod: one verified address, sandbox). The task
  role may send from it only.
- **Image:** `node:26.13.0-alpine`, production dependencies only, non-root, runs TypeScript
  directly. Node 26 type stripping was checked on both entrypoints.
- **Deploy:** GitHub Actions `workflow_dispatch` with OIDC (no AWS keys stored). It builds the
  widget, builds and pushes the ARM image (tag = commit SHA), then runs `cdk deploy`.

**Spec:** `docs/ARCHITECTURE.md` §2 (components, environments, cost), §5 (security); `CLAUDE.md`.

## Global Constraints
- **No secrets in code, context or outputs:**
  - secret values are set by hand
  - generated values stay in Secrets Manager
  - the task definition only references them
- **Only preprod is deployed until M6.** The stack shape works for `prod` without rewrites.
- **Preprod always uses the mock Magicline** (`MAGICLINE_USE_MOCK=true`); real keys are M6.
- **Logs:** to the KMS-encrypted log group, 30 days.
- **No new npm dependencies** (everything is in `aws-cdk-lib`).

## Review Focus
1. **Nothing public but CloudFront:** the ALB is internal, tasks accept traffic only from the ALB,
   and the S3 bucket is private (OAC).
2. **Secrets** never appear in plain text in the template, the task environment or the outputs.
3. **Least privilege:**
   - the task role may send email only from the identity, and read only its secrets
   - the scheduler role may run only the worker task definition
4. **Headers:**
   - the widget may be framed only by the help portal (`frame-ancestors`)
   - HSTS and nosniff are set
   - API responses are not cached by CloudFront
5. **Proxy hops:** `TRUST_PROXY_HOPS` matches the real chain (CloudFront and ALB), so rate limits
   and Turnstile see the visitor IP.

## Tasks
1. Dockerfile, `.dockerignore`, local build and smoke (API health, worker usage, mock sidecar).
2. Foundation: app secret, generated OTP secret, SES identity (context `emailFrom`).
3. Service stack: internal ALB, Fargate API with mock sidecar, VPC origin distribution, widget
   bucket and deployment, response headers, outputs. Assertion tests.
4. WAF stack (us-east-1) attached to the distribution. Tests.
5. Scheduler: the three nightly worker runs. Tests.
6. Deploy workflow, `docs/DEPLOY.md` runbook, ARCHITECTURE update, final review.

Not in M3c: the load test (needs a deployed target), custom domains (prod, M6) and the GitHub
OIDC role (a one-time manual step in the runbook).
