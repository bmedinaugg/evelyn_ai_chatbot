# M2a Customer Login Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A visitor in a widget conversation can log in with an emailed one-time code. The server then finds their Magicline account(s) via cross-studio search. With several accounts the visitor picks one; the chosen account is bound to the conversation **server-side**. M2b uses that binding for account answers.

**Architecture:**
- **OTP challenges** live in Supabase. Email and code are only stored as HMAC-SHA256 hashes with `OTP_HMAC_SECRET`.
- **Plaintext email** exists only in memory during the request/verify calls: it's used to send the code and to search Magicline, and is never stored or logged.
- **Magicline keys** come from a `MagiclineKeyResolver`:
  - Secrets Manager in AWS (one JSON secret per env, cached 5 min)
  - env-based locally (`MOCK_MAGICLINE_KEYS`)
- **Emails** go through an `EmailSender`: Amazon SES in AWS; a local-only console outbox (`APP_ENV=local`).
- **Widget:** account questions from anonymous visitors now get the action `login` instead of `contact`. The widget shows the email step (with Turnstile), the code step and the account picker.

**Tech Stack:**
- New (approved 2026-11-12): `@aws-sdk/client-sesv2@3.1166.0`, `@aws-sdk/client-secrets-manager@3.1166.0`
- Existing stack from M0–M1c

**Spec:**
- `docs/ARCHITECTURE.md` §3.2 (OTP), §3.3 (key resolver), §4, §5
- `docs/api/magicline.md` (`POST /v1/cross-studio/customers/search`, `GET /v1/studios/information`, `StudioInformation.name`)
- `CLAUDE.md` (OTP: short expiry, single use, hashed at rest, rate limited per email and IP)

## Global Constraints
- **Codes:** 6 digits, from `crypto.randomInt`.
- **Expiry:** `OTP_EXPIRY_SECONDS` (default 300).
- **Single use:** `consumed_at` is set atomically on success.
- **Attempts:** at most `OTP_MAX_ATTEMPTS` (5) wrong attempts per challenge, after which it's dead.
- **Per email:** at most 3 challenges per 15 minutes. A further request is accepted silently but no email is sent (no enumeration, no email bombing).
- **Per IP:** route limit of 5/min on request and 10/min on verify.
- **No enumeration:** a code request always answers `202 { ok: true }`, whether or not an account exists.
- **Hashing:**
  - `emailHash = HMAC(secret, 'email:' + normalisedEmail)`
  - `codeHash = HMAC(secret, 'code:' + challengeId + ':' + code)`
  - compared in constant time
  - `OTP_HMAC_SECRET` must be ≥ 32 chars
- **Binding:**
  - Verify needs the conversation bearer token **and** the same email (its hash must match the challenge).
  - Account candidates are stored server-side (`{customerId, studioId, status, studioName, maskedNumber}`); the client only ever sends an index.
  - A selected account can't be changed without logging in again.
- **Data minimisation:**
  - stored: ids, status and studio name only
  - masked customer number: only the last 3 characters (`•••123`)
- **Text:** nl+en for every new text, including the email itself.
- **Commits:** branch `m2a-login` (stacked on `m1c-widget`), standard trailer.

## Review Focus
1. **Brute force:** a sixth wrong code fails even if correct; an expired code fails; a used code fails a second time; a code for conversation A can't log in conversation B.
2. **Enumeration:** responses and timing don't reveal whether an email has a Magicline account.
3. **Account picker tampering:** an out-of-range index, or selecting before verification, gives 400/403. The server never trusts customer or studio ids from the client.
4. **Email never stored or logged:** check DB rows and log output in tests.
5. **Magicline down during verify:** the visitor is verified, gets a "couldn't load your account" message and can retry. No crash, no partial binding.

## Tasks
1. **DB** (`packages/db`):
   - migration `otp_challenges` (`conversation_id` fk, `email_hash`, `code_hash`, `expires_at`, `attempts`, `consumed_at`, `created_at`)
   - conversation columns `verified_email_hash`, `verified_at`, `account_candidates jsonb`, `customer_id`, `studio_id`, `customer_status`
   - SQL functions `verify_otp_attempt(p_challenge_id, p_code_hash)` (atomic attempt count, expiry, single use) and `bind_account(p_conversation_id, p_index)`
   - pgTAP and repository integration tests
2. **Auth core** (`packages/core/src/auth`): `hashEmail`, `hashCode`, `generateCode`, and an `OtpService` covering request (rate rules, email send) and verify (match, then cross-studio search, studio names, candidates, auto-bind when exactly one). Unit tests with fakes.
3. **Magicline** (`packages/magicline`):
   - `getStudioInformation()` client method
   - `customerNumber` in lookups
   - key resolvers (env and Secrets Manager with cache)
   - mock server: `GET /v1/studios/information`, and fixture profiles with `customerNumber`
4. **Email** (`packages/shared` or a new `packages/email`): `EmailSender` with SES (`SendEmail`, simple content, nl/en text) and a local outbox (refused unless `APP_ENV=local`).
5. **API:** `POST /widget/conversations/:id/login/request` (Turnstile), `/login/verify`, `/login/select`. Reply action `login` for anonymous account questions. Config loaders and `main.ts` wiring.
6. **Widget:** login steps (email + Turnstile, code, picker, logged-in note), nl/en texts, e2e.
7. **Docs, CI, README.**
